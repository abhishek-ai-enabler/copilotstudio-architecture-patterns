# Architecture catalog verification plan

Use the same sequence for follow-up releases. There are two separate deliverables: **a verified publication** and **a review of a particular solution**. Passing the first never implies the second.

| Phase | Change or check | Acceptance evidence |
| --- | --- | --- |
| 1. Freeze the baseline | Record the review date and parent commit. Compare the entries under the Learn architecture index and named decision guides with `CATALOG.md`, by source URL and option, not by topic similarity. | Every listed architecture, idea and option maps to one file in the correct class. Record additions, moved sources and limitations in the dated audit. |
| 2. Review technical meaning | Follow the source, entry, component map and sequence. Check which product handles the request, which identity reads/writes, who can approve, what constitutes completion, and whether preview, channel and licensing caveats change the choice. | A material inconsistency is corrected or explicitly flagged. Synthesized additions address distinct decisions: recovery after an ambiguous write and remote A2A delegation rather than MCP tool invocation. |
| 3. Illustrate the actual flow | Assign every sequence participant a platform or explicitly leave it unbranded. Use unmodified approved assets, keep a text alternative, and regenerate static images from the same Mermaid source. | Every entry displays an image on GitHub without remote icon loading. Names remain readable; a product present elsewhere in the architecture does not get added to a flow that never calls it. |
| 4. Make review repeatable | Classify every new or revised entry in the [validator](../tools/validate_solution.py) against what its documented design actually does. Link risk-triggered controls to remedy patterns, and keep real intake packets private. | A missing classification or a declaration below the selected design's minimum cannot produce readiness. Verify a write example needs receipt evidence and a read-only example does not. Failed controls take precedence over incomplete evidence. No score, model or automatic deployment decision substitutes for human review. |
| 5. Exercise and release | Run the Python suite and the [browser render check](../tools/diagrams/README.md). Inspect representative flows for branding and arrow/branch readability. Check cited sources and review the staged diff for unrelated files or sensitive material. | Examples produce the documented exit codes; all indexes and local links resolve; every image matches its source/icon fingerprint. Publish without force and confirm the remote default branch's SHA. |

**What changed in this pass:** [coverage and content audit](../REVIEW-2026-11-27.md), [transaction recovery](../technical-patterns/write-reconciliation.md) and [remote A2A delegation](../technical-patterns/remote-a2a-specialist.md), [official icon registry](../assets/platforms/products.json), [platform maps and image build](../tools/diagrams/README.md), [solution validator and examples](README.md), and executable [catalog and decision tests](../tests/). No tenant access is part of these checks.
